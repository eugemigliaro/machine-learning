===== PAGINA 4 =====

El reto tras la selección de modelo
The challenge after model selection

Dos clasiﬁcadores pueden obtener exactamente el mismo F1 y requerir intervenciones completamente
diferentes.

Uno puede estar limitado porque no tiene capacidad suﬁciente para representar la relación (X\rightarrow Y).

Otro puede aprender perfectamente training pero generalizar mal.

Otro puede discriminar muy bien positivos de negativos pero estar utilizando un threshold inadecuado.

Otro puede tener una excelente performance global pero fallar sistemáticamente en un determinado tipo de
observaciones.


Por eso, la métrica ﬁnal detecta que existe un problema; no identiﬁca cuál es el problema.

¿Qué está limitando mi performance?
What is currently limiting performance?

El training set es sólo una muestra ﬁnita de esa distribución. Esto introduce tres fuentes
conceptualmente distintas de error:

  -    error asociado al hecho de aprender a partir de una muestra ﬁnita (variance, cambia para otra
       muestra)
  -    error asociado al modelo o hipótesis elegida (bias)

  -    error inherente al problema/datos (error no explicable/reducible a partir de X)

===== PAGINA 14 =====

El error de validación no es el ﬁnal del proyecto
Deﬁnir baseline performance

Una buena práctica al principio del proyecto es saber cual es el Human Level Performance (HLP)


Esto nos sirve para decidir dónde centrar nuestros esfuerzos, que performance es más mejorable


¿cuando es útil HLP?


Unstructured data: Imágenes, Audio, Texto… en este tipo de datos, los humanos somos muy buenos, HLP es
una buena forma de baseline performance


Structured data: tabla con datos de usuario o productos
aquí los humanos no somos tan buenos, así que HLP no va a ser tan útil

===== PAGINA 15 =====

Human Level Performance (HLP)

Cómo calcular el HLP:


Buscar en la literatura o internet/open source
-con esto además podríamos tener una primera versión (algoritmo/modelo open source) rápidamente para
tener como referencia
Si no, podemos usar una performance de una versión previa (si la tenemos)


En algunos casos, estas performance (HLP por ejemplo) nos da una idea del error irreducible.
-> Nos ayuda a decidir en qué parte del modelo o de los datos enfocarnos para reducir error


Plantear un problema y exigir un 90% de performance no es la mejor idea:
Primero es recomendable conocer un baseline y donde está el estado del arte o el HLP, y a partir de allí deﬁnir
el “objetivo”

¿Cómo continuamos?
Imaginemos que hemos recolectado unos datos, seleccionado unas características e implementado
un algoritmo pero no estamos satisfechos con el desempeño: ¿Cómo continuamos?


Generalmente se suelen seguir una de estas estrategias:
-Conseguir más datos
-Probar un número menor de características
-Probar a añadir características (o variaciones de ellas)
-Cambiar hiperparámetros para que sean menos (o más) restrictivos

===== PAGINA 31 =====

Diseño centrado en Modelo vs Datos
Model vs Data-centric design
Model-centric:
  -    dados unos datos, encontrar el modelo (y set de hiperparametros) que mejor funcionan.
  -    mantener los datos ﬁjos e iterativamente mejorar el modelo


Data-centric:
  -    implementamos un modelo que sabemos que funciona razonablemente bien y lo dejamos ﬁjo
  -    Aplicamos distintos métodos para aumentar la calidad (o cantidad) de los datos (añadir feats tb!)
  -    Esto repercutirá en mejor performance del modelo.

Análisis de Errores
Error Analysis
El objetivo es entender qué tipo de errores comete el modelo y qué tienen en común


Sería ir un paso (o varios) más allá de la matriz de confusión


Ya que si encontramos un patrón, podremos intentar mejorar el funcionamiento del modelo en ese aspecto
concreto.
Se puede hacer manualmente, viendo los errores (predicciones incorrectas) y viendo cómo son los datos y
anotando tags (aspectos que pueden ocurrir)


Objetivo: ver cómo son los errores cometidos e identiﬁcar algún patrón o motivo por el que no están siendo
bien clasiﬁcados


Primer paso: elegir qué factores (tags) se van a analizar
